# Reply: claim graph for contradiction detection

You have this almost exactly right, and the parts you flagged as the big ones
(polarity, claim date, source span) are all cheap and additive. But before you
build a contradiction graph I want to push on one thing hard: **two of your three
real failures are not contradictions**, and the single check that would have caught
the worst one is much smaller than the graph. I'll answer your five questions in
order, then give you the narrow first step.

Everything below is grounded in the current code; file:line citations are to
`goldberg-system` at this commit.

---

## Q1 — Schema extension without a full re-enrich: feasible, and cheap. Here's the real cost.

Split it into two costs, because they're wildly different sizes.

**(a) The schema + index change is essentially free.** `Claim`
(`metadata/schema.py:90`) is a plain pydantic model, and the ES `claims` field is a
`nested` type (`elasticsearch_indexer.py:60`). Adding optional fields
(`polarity`, `claim_date`, `source_span`, `epistemic_status`, `confidence`) is:

- **No data migration.** New fields are optional with safe defaults, so every
  existing serialized `Claim` still validates. `extra="forbid"` only rejects
  *unknown* keys; adding a known key is fine.
- **No reindex.** `ensure_index` already issues an additive `put_mapping` on every
  run and the code comment says it outright: *"ES merges additive field mappings
  without a reindex"* (`elasticsearch_indexer.py:117-123`). Nested sub-fields merge
  the same way. The mapping becomes queryable immediately; old docs simply carry
  null for the new fields until re-touched.

So the mapping/model change is an afternoon, not a project.

**(b) *Populating* the new fields on existing docs is the actual cost — and it is
a re-enrichment, not a migration.** Polarity, claim date and source span are read
*off the text*. They don't exist in the stored frontmatter, so no reindex-from-disk
can conjure them; the LLM has to re-read each document. The mechanism already
exists — `goldberg reindex` → `backfill_from_papra` (`pipeline.py:95`), which pages
every Papra doc, re-enriches it, and re-writes idempotently (ES `_id = doc_id`, so
re-runs update, never duplicate).

**The cost figure you asked for:** the enricher is `gpt-4o-mini`
(`openai_enricher.py:109`). At ~1,600 docs and current pricing, a full-corpus
re-enrich is **roughly $2–25 and about an hour of batch** — the spread is because
most docs are small but the body budget allows up to 100k tokens
(`openai_enricher.py:34`). Either way it is *cheap*, and it is a one-off.

**But you do not have to pay even that to get the value you actually want** — see
Q4. The failures that hurt happened in *our own work product*, which is a small set.
Re-enrich that first; the evidence corpus can wait or never happen.

**One gap to note honestly:** there is currently *no* "re-index from stored
frontmatter without calling the LLM" path — `backfill` always enriches. If we ever
want to re-shape claims cheaply (e.g. normalize `asserted_by`, see Q2) without
paying for the LLM again, that path is worth adding. Small, and I'd do it as part of
this.

## Q2 — The speaker-scoped three-way split: right instinct, but it's two axes, not one, and it rests on something you didn't list.

I strongly agree with the core: a detector that flags every contested fact is
switched off within a day, and `asserted_by` is the right lever. Your 739→183 story
is the whole argument. But two corrections.

**It's two axes, not one.** Your three buckets don't come off a single "speaker"
dimension — they come off two:

- **Axis A — source tier:** *evidence corpus* vs *our own work product.* (Today this
  is partly encoded already: `origin`/`role` in the schema, and simply "is it in
  `goldberg-casework/analysis/`".)
- **Axis B — speaker scope:** *same speaker over time* vs *across speakers* (needs
  `asserted_by`).

Map your buckets onto that and they land cleanly:

| Bucket | = | Rule |
|---|---|---|
| Ammunition | evidence tier **·** same speaker over time | surface loudly |
| Contested | evidence tier **·** across speakers | never flag |
| **Rot** | **our-work-product tier** · *any* speaker | the only integrity fire |

The point: **"rot" is a *tier* condition, not a speaker condition.** Two of our own
files disagreeing is rot whether or not it's the "same speaker", because the speaker
is *us*. Collapsing it into the speaker axis is what would make it leak. Keep the
tier tag explicit.

**The load-bearing prerequisite you under-weighted: `asserted_by` must be
identity-resolved.** Right now it's free text straight from the model
(`openai_enricher.py:208-213`) — "Goldberg", "Mr Goldberg", "the prosecutor" are
three different strings. "Within one speaker over time" is *uncomputable* until
those collapse to one canonical speaker id (i.e. linked to the `entities` layer).
Without it you both **miss** real shifts (the label drifted) and **mis-split**
(same person read as two). For the *ammunition* use-case — which is the one you said
is often the argument itself — speaker normalization is arguably **more** load-bearing
than polarity. I'd rank the gaps: source-span ≈ polarity > speaker-resolution >
claim-date > confidence.

## Q3 — Negation vs embeddings: your lead holds, and it's currently moot — which is good news.

**It holds.** Negation is genuinely poorly represented in the mainstream embedding
models (OpenAI `text-embedding-3`, Elastic's ELSER, the sentence-transformer
family) — "X was before the court" and "X was **not** before the court" sit almost
on top of each other in cosine space. Cosine finds aboutness, not agreement. Your
two-stage conclusion — *retrieve candidates with vectors, adjudicate with something
that understands negation* — is the correct architecture, and a single-stage
embedding detector would look like it worked while missing exactly our cases. No
disagreement.

**Two things that make it easier than the lead implies:**

1. **We use no embeddings at all today.** Retrieval is BM25 + the structured nested
   `claims` (the indexer says dense-vector RAG is "a deliberate follow-up, not
   indexed here yet", `elasticsearch_indexer.py:11-12`). So the negation weakness
   isn't biting us — and for *our* corpus we may not need the vector stage at all.
   Contradiction *candidates* can be generated **structurally and deterministically**:
   same normalized `(subject, predicate)` with opposite `polarity`, same
   `subject`/`object` keyword. That's precise, free, and needs no model. Vectors only
   earn their place for fuzzy paraphrase where the triples don't line up — add them
   *if* structural recall proves too low, not before.

2. **If polarity is captured at extraction time, many contradictions need no judge
   at all.** Two claims sharing normalized subject+predicate+object with opposite
   polarity *is* the contradiction, deterministically. The NLI/LLM adjudicator is
   then only for the residual fuzzy cases — small volume, and it's your L4 anyway.

So: structured candidate generation first; NLI/LLM judge as a later, optional
adjudication stage; vectors last and only if measured recall demands them.

## Q4 — The smallest first step that catches one of the three failures. (This is the important answer.)

Reframe the three failures by *shape*, because they are not the same problem:

| # | Failure | True shape | What actually catches it |
|---|---|---|---|
| 1 | 384-bundle inference → 45 files → draft filing | **provenance / propagation** (an *inference* restated as fact, with no source) | epistemic status + source-span requirement on our-work-product claims |
| 2 | "76 of 207" doesn't reproduce (10 of 207) | **non-reproducing computation** | re-computation — *your* mechanical checker, not the graph |
| 3 | repealed s.5 PfHA cited as live/HELD | **stale authority** | repealed-provision list (yours) / a claim-level `as_of` + citator label |

**Only #2 and #3 are already yours, and neither is a contradiction.** A general
contradiction graph would not have caught #1 or #3 cleanly. So the honest answer to
"what's the smallest thing that catches ONE of these" is **not** the claim graph — it's:

> **Add `epistemic_status` + `source_span` to `Claim`, extend claim extraction to
> our own work product (`goldberg-casework/analysis/`), and run one query:
> "an assertion in an output/served document whose `epistemic_status` is `inferred`,
> or that has no `source_span`."**

That single check fires on the 384-bundle claim the moment it lands in a deliverable
— which is failure #1, the one that reached a court document and contaminated ten
reviewers. It needs:

- **no whole-evidence-corpus re-enrich** (only our work product, a small set),
- **no vectors, no NLI**,
- **two new optional fields** and a tightened enricher instruction.

That's L2-lite scoped to the tier where the rot actually happens. It's the "narrow
thing that works" you asked for, and I'd build exactly it first.

**On failure #1's *spread* (the 45 files):** your de Kleer / TMS pointer is the right
long-term frame, and there's a cheap approximation that gets you most of it without a
truth-maintenance engine — a **`derived_from`** link on each of our claims (the
claim/doc it was inferred from). That gives you the "object to retract" you want
instead of a grep: mark the source claim retracted, query everything whose
`derived_from` chain contains it. Add it to the same schema change; it's one more
optional field.

## Concrete schema proposal (what I'd actually add to `Claim`)

```python
class Claim(BaseModel):
    model_config = ConfigDict(extra="forbid")

    subject: str
    predicate: str
    object: str
    asserted_by: str | None = None        # (existing) — to be entity-resolved, Q2

    # --- additions, all optional & additive (no migration, no reindex) ---
    polarity: bool = True                  # False = the claim is negated ("was NOT")
    epistemic_status: str | None = None    # "asserted" | "inferred" | "held" | "quoted"
    source_span: str | None = None         # quoted sentence, or doc_id + char range
    claim_date: str | None = None          # when the assertion was MADE (not doc date)
    confidence: float | None = None        # extractor's self-rated certainty
    derived_from: list[str] = []           # claim/doc ids this was inferred from (TMS-lite)
```

Every field defaults to a value that leaves existing docs valid. The ES nested
mapping gains `polarity` (boolean), `epistemic_status`/`source_span`/`claim_date`
(keyword/text), `confidence` (float), `derived_from` (keyword) — all additive.
